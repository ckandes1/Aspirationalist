# Project Foundation — The Idea Murder Machine
Last updated: March 2026

## North Star
Move from idea to deployed artifact faster, with good enough judgment to decide without overthinking. The goal is useful artifacts that change what people do. Software is one possible artifact. Often the right answer is simpler. A senior developer knows when not to build software — that judgment is the target.

## Who I Am (Relevant Context)
- Strategic thinker, weaker at execution
- Learn by building mental models — need connections before details
- Prone to analysis paralysis; tend to over-deliberate before shipping
- Specific last-mile block: I develop ideas into content but stop just before the step that makes them actionable. This feels like shipping but isn't.
- Anxiety about public deployment — fear that failure invalidates the thinking system behind the idea, not just the idea itself
- Already ship content regularly — that is my baseline artifact
- Not a syntax learner — I learn conceptually and by connection

## Core Thinking Principles
**First principles:** Strip assumptions. Start from what's true.

**Test at the limit:** Push any idea or concept to its extreme. If it breaks there, it probably doesn't hold generally. Fast way to find flawed mental models and make better choices.

**Non-zero-sum:** Good solutions create value, not just redistribute it.

**Survival precedes stewardship, but stewardship is the reason:** Pragmatism is necessary to stay in the game. But staying in the game is only worth it if it serves something beyond yourself.

## The Artifact Ladder
Start at the lowest rung that makes the idea useful. Climb only when necessary.

Thought → Content → Checklist/Guide → Template/Playbook → Toolkit → Software

Key test: "What is the smallest thing someone could do differently because of this?"
- Can't answer it? Idea isn't ready.
- The answer usually determines the artifact type.
- A spreadsheet with formulas is the most primitive software.
- Software is justified when action must repeat over time with dynamic inputs.

## The Idea Murder Machine
Modeled on X/Alphabet moonshot factory ("kill the magic"):

1. Find the load-bearing assumption
2. Design the cheapest possible test of it
3. If it fails, the idea is dead — move on
4. If testing requires huge upfront investment, that's a red flag

Good ideas are cheap to falsify.

## Informed Vibe Coding — The Target State
Two things share the name "vibe coding":

Naive: prompt AI, accept output, hit a wall, don't know why.

Informed (the target): direct AI with precision, read output critically, know when something smells wrong, make architectural decisions the AI can't make, use AI outputs to check each other.

The difference is judgment. Judgment comes from mental models. Syntax is not required. Reading comprehension is.

Senior developer judgment includes knowing when NOT to build software.

## My Content Baseline Problem
I can generate ideas and produce content. My specific block: I stop just before actionability. The content exists but doesn't tell anyone what to do with it. This feels like shipping but isn't. The fix is always asking: "What does someone DO with this?"

## Developer Documentation Principle
Good documentation is not a transcript. It is:
- What was decided
- Why it was decided
- What was ruled out and why

This applies to code, to ideas, and to personal process.
